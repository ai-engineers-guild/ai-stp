# ADR-0031: Закрытые случаи жалоб и модерация

Статус: принято.

## Контекст

Продукт сознательно исключал социальные механики: рейтинги, ленты и публичные обсуждения. Вместе с ними был исключён и минимальный операционный канал — возможность пользователя сообщить платформе о сломанном или вредоносном опубликованном объекте. Блокировка версии оставалась доступной только по собственной находке владельцев или через закрытый процесс уязвимостей.

Практическое следствие: столкнувшись с некорректной совместимостью, повторяемым сбоем или вредным поведением, пользователь либо молчит, либо уносит подробности в публичные каналы, где им не место. Операторы платформы не получают структурированных машинных доказательств, а модерация не может сопоставить жалобы с точными версиями и операциями.

Отказ от социальных механик был правильным; ошибкой было счесть операционный канал жалоб одной из них.

## Варианты

1. Оставить всё как есть: только собственные находки владельцев и закрытые сообщения об уязвимостях. Ноль поверхности, но платформа слепа к реальным поломкам.
2. Публичные issue на GitHub из продукта. Прозрачно, но раскрывает окружение репортёра, неуправляемо по приватности и превращает жалобу в социальную механику.
3. Единый закрытый `ReportCase` из веба и CLI с механическим составом, предпросмотром, триажем модераторами и эскалацией уязвимостей в закрытый процесс.

## Решение

Принимается вариант 3.

**Один закрытый случай, два входа.** Действие жалобы в вебе и команда жалобы в CLI создают один внутренний закрытый `ReportCase` через общий сценарий приложения. Публичный issue на GitHub из жалобы не создаётся автоматически.

**Состав жалобы механический и закрытый.** CLI собирает только: точный объект, версию и хэш; харнесс и его версию; версию провайдера; идентификатор и стадию операции; идентификаторы снимков проверок; типизированный код ошибки; необязательную ограниченную очищенную диагностику — только после явного просмотра и согласия. Исходный код, подсказки, содержимое `.env`, значения секретов, закрытые байты объектов и полные домашние пути не отправляются автоматически. Репортёр видит полный предпросмотр до отправки.

**Жизненный цикл случая закрыт перечнем.**

```text
submitted → triaged → awaiting_author → resolved | dismissed
                    ↘ security_escalated
```

Модераторы платформы выполняют триаж. После триажа автор объекта при необходимости получает очищенное уведомление. Случай с признаками уязвимости эскалируется в закрытый процесс по `SECURITY.md`.

**Число жалоб ничего не блокирует само.** Повторные жалобы могут группироваться, но количество жалоб никогда не скрывает и не блокирует объект автоматически. Скрытие, блокировка и восстановление остаются явными аудируемыми действиями модератора с автором, основанием и временем.

**Злоупотребление ограничено механикой.** Отправка требует аккаунта, ограничена по частоте и идемпотентна; дубликаты группируются, а не умножают сигнал.

## Последствия

- машинная граница случая принадлежит `docs/contracts/report-case.md`, требования — `SPEC-016`;
- `SPEC-007` перестаёт исключать пользовательский канал: блокировка остаётся аудируемым действием владельцев, жалобы создают случаи и не меняют жизненный цикл версии автоматически;
- границы MVP и веба получают жалобу как обязательную функцию;
- маршруты API, машинная справка CLI и политика данных получают требования жалобы;
- эксплуатация получает runbook триажа жалоб и сигналы наблюдаемости.

## Условия пересмотра

Решение пересматривается, если закрытые случаи начнут систематически использоваться для подавления конкурирующих авторов — тогда ужесточаются идемпотентность, группировка и аудит, — либо если объём жалоб потребует автоматической приоритизации, которая всё равно не станет автоматической блокировкой.
