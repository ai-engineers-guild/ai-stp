# ADR-0066: Локальное обогащение component draft

Статус: принято.

## Контекст

Native discovery и adopt намеренно знают только механические факты: layout,
путь, exact bytes и доказанное происхождение. Полный ComponentVersionPassport
дополнительно требует имени, безопасного описания, лицензии, dependencies,
возможностей, полномочий и точного публичного источника. Без отдельной границы записи
агент либо не может довести draft до полноты, либо вынужден менять SQLite и
угадывать поля вне машинного контракта.

Component и setup одновременно используются как kind локальной сущности и как
kind неизменяемого version passport. Поэтому запрет parent revisions на общем
PassportEnvelope ошибочно запрещает именно историю draft, хотя неизменяемость
нужна лишь формальному version snapshot.

## Решение

CLI получает три команды из единого command registry: passport show, update и
validate с явным профилем `--for-publication`. Update принимает только bounded
обычный JSON-файл, не следует символическим ссылкам, использует закрытую типизированную схему,
отклоняет secret-bearing keys до отражения значений и требует одновременно
`--expected-revision`; точная ожидаемая ревизия является подтверждением
локального обратимого изменения по `ADR-0118`, отдельного `--confirm` нет.

Read-only `passport suggest` работает до update и только над сохранёнными exact
bytes. Он копирует предложения из закрытого блока `ai-stp.component` в
`pyproject.toml` или `package.json` и из полной exact Git provenance, называет
источник каждого поля и оставляет все значения неподтверждёнными. Обычные поля
пакетного manifest не интерпретируются как семантика компонента. Неизвестное,
неверное или противоречивое объявление закрывается отказом; невыводимое поле
остаётся явным unresolved и не получает догадку.

Принятые поля записываются как declared/user-confirmed facts в новую
content-addressed child revision. No-op возвращает текущую ревизию, stale head
закрывается конфликтом. Общий envelope разрешает parent graph для component
draft; concrete ComponentVersionPassport и SetupVersionPassport отдельно
требуют пустой parent list и остаются immutable snapshots.

Publication validation не пишет в сеть и не публикует. Она перечисляет все
missing/invalid fields и пытается построить формальный ComponentVersionPassport
из точной ревизии. Облачные план публикации, одобрение, применение, восстановление и статус
добавляются только после стабильного server contract и не имитируются локальной
командой.

## Рассмотренные варианты

1. Автоматически вывести все поля из обычного package manifest. Отвергнуто:
   package dependencies не доказывают назначение компонента, а лицензия,
   полномочия и условная авторизация требуют явного versioned блока и решения.
2. Редактировать YAML рядом с установленным компонентом. Отвергнуто как скрытая
   запись в target и смешение исходного объекта с локальным registry draft.
3. Разрешить произвольный JSON merge. Отвергнуто: он создаёт второй неограниченный
   schema owner и может пронести секреты или неизвестные требования.
4. Считать `ready` разрешением публикации. Отвергнуто: локальная структура не
   доказывает аутентификацию, права, текущую серверную политику или отсутствие гонки.

## Последствия

Agent получает исполнимый путь от adopt к формальной полноте без model API и без
ручного SQLite. Revision graph синхронизируется существующим механизмом, released
version не перемещается при последующем update. Публикационная state machine
остаётся открытой зависимостью platform/CLI contracts, а не скрытым side effect.

## Условия пересмотра

Решение пересматривается при versioned patch schema, доказуемом manifest
extraction proposal или появлении server publication contract. Новые поля не
добавляются как свободные extras: они сначала получают типизированного владельца
и совместимость generated schemas.
