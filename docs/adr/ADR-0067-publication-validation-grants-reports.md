# ADR-0067: Серверный контур публикации, validation jobs, grants, жалоб и staff-аудита

Статус: принято.

## Контекст

Продуктовые правила уже зафиксированы:

- полная публикация и источники доказательств — `ADR-0026`, `SPEC-007`,
  `docs/contracts/validation-policy.md`;
- пригодность к установке из актуальных доказательств — `ADR-0032`;
- права на major-линию, форк и производная публикация — `ADR-0030`,
  `ADR-0020`, `SPEC-002`;
- закрытые жалобы и модерация — `ADR-0031`, `SPEC-016`;
- очередь и транзакционная постановка — `ADR-0038`, `SPEC-018`;
- вертикальные API-слайсы — `ADR-0037`;
- синхронизация приватных ревизий (`#179`) — `ADR-0045`, `SPEC-025`.

После Sprint 1 и `#179` есть PostgreSQL, Alembic, таблица `job`, worker-заглушки
`upload` / `update`, `catalog_metadata` с experimental seed, OAuth, сессии,
устройства, append-only `audit_event` и object store. Нет таблиц и API для
`AccessGrant`, `GrantInvitation`, `ReportCase`, `ValidationSnapshot`, плана
публикации, реальных обработчиков validation/publish, staff-действий
`author_verified` / lifecycle и доставки приглашений через Resend.

Issue `#181` (ключ `P8-06`) требует собрать этот серверный контур так, чтобы:

- точный план, идемпотентность, истечение доказательств, политика, права,
  жалобы, аудит и авторизация были покрыты тестами;
- повторы и dead-letter имели эксплуатационные доказательства;
- CLI и web UI оставались вне границ среза (клиентские команды — `P8-C2`,
  web own objects — фаза 9).

Внешние практики transactional outbox, доставки «не менее одного раза»,
dead-letter и идемпотентных потребителей совпадают с уже принятым
`ADR-0038`: доменная запись и постановка job в одной транзакции; обработчик
обязан переживать повтор. Новая зависимость-брокер или workflow-engine
(Temporal и подобные) для MVP не оправдана.

## Варианты

1. Один монолитный «platform service» с публикацией, правами и жалобами в
   общем слое. Быстрее стартовать, но нарушает `ADR-0037` и смешивает
   авторизацию, lifecycle и побочные эффекты.
2. Пять независимых сервисов или брокеров (publish, validate, grants, reports,
   email). Масштабируемо, но вводит dual-write, вторую эксплуатацию и
   противоречит `ADR-0009` / `ADR-0038`.
3. Один issue-срез поверх существующего PostgreSQL: вертикальные API-слайсы,
   расширение закрытого `JobType`, долговечные доменные таблицы, Resend как
   порт доставки, staff allowlist без полного RBAC. Продуктовые SPECs не
   переписываются.

## Решение

Принимается вариант 3.

### 1. Один implementation-срез, пять доменных границ

`#181` материализует серверную часть уже принятых правил, не создавая
параллельной политики. Владельцы смысла остаются:

| Область | Владелец смысла | Серверная материализация `#181` |
|---|---|---|
| проверки и публикация | `SPEC-007`, validation-policy | plan/confirm API, снимки, jobs |
| права и приглашения | `SPEC-002`, access-grants-and-forks | таблицы, invite/accept/revoke API |
| жалобы и модерация | `SPEC-016`, report-case | report API, staff lifecycle |
| очередь | `SPEC-018`, `ADR-0038` | новые типы job и обработчики |
| audit | `SPEC-002`, `SPEC-010` | расширенный закрытый набор action |

### 2. Вертикальные слайсы API

В `apps/api` появляются слайсы (имена каталогов могут совпадать с маршрутом):

- `publish` — план публикации, подтверждение, статус, отмена до необратимого
  эффекта;
- `grants` — приглашение, список, отзыв приглашения и права, hook accept при
  входе;
- `reports` — создание и список своих случаев, staff-триаж и действия;
- `staff` (или moderation внутри reports/publish) — выдача и отзыв
  `author_verified`, состояния версии `blocked` / `hidden` / restore.

Web и CLI вызывают один сценарий приложения и один маршрут `/v1`
(`SPEC-010` REQ-1011). DTO — в `packages/contracts`; ORM — в
`ai_stp_platform.models`; инварианты домена — в слайсе.

### 3. Расширение закрытого реестра job types

К `upload` и `update` аддитивно добавляются:

| JobType | Назначение |
|---|---|
| `validate` | серверные credential-free проверки и привязка author attestations → `ValidationSnapshot` |
| `publish` | после успешной validation: неизменяемая версия, object location, проекция каталога, `component_verified` |
| `reevaluate_eligibility` | истечение или ужесточение политики → снять badge и install eligibility без переписывания байтов |
| `deliver_invitation` | отправка письма приглашения через порт Resend |

Подпись или запись объекта в store остаётся шагом внутри `upload` / `update` /
`publish`, а не отдельным типом (`SPEC-018`). Новый тип добавляется только
через изменение closed registry и тестов реестра.

Постановка job — transactional outbox в той же транзакции, что и доменная
запись; доставка «не менее одного раза»; обработчики идемпотентны по
business key (`plan_id`, `snapshot_id`, `invitation_id`, digest версии).
Исчерпание попыток переводит в `dead_letter` без автоповтора; dead-letter
хранит безопасную `last_error`.

### 4. План публикации как серверная Operation

Публикация не сводится к одному POST. Сервер хранит неизменяемый
`PublicationPlan` (частный случай `docs/contracts/operation.md`):

- actor, device, идентичность объекта, точный content digest, версия
  политики, ссылки на доказательства, effects, `expires_at`, `plan_hash`;
- confirm относится только к этому hash;
- изменение digest, политики или доказательств делает plan `stale` и требует
  нового плана;
- после confirm: `validating` → job `validate` → `publish_planned` /
  publishing → job `publish` → `published` либо типизированный отказ;
- повтор confirm или ключа идемпотентности возвращает ту же operation, не
  второй эффект.

Experimental seed (`SPEC-021`) не является этим контуром: seed остаётся
first-party bypass с явной меткой experimental и не подменяет полный барьер
публикации.

### 5. Права: invitation → grant

Реализуется `ADR-0020` / `ADR-0030` без ослабления:

- `GrantInvitation` и `AccessGrant` — отдельные таблицы;
- ответ create-invitation неотличим для известного и неизвестного email;
- accept только при совпадении подтверждённого провайдером адреса;
- цель права — major-линия `(stable_id, major)`;
- отзыв действует вперёд; байты, уже у получателя, не стираются;
- токен письма не попадает в logs/audit payload; Resend — только транспорт
  (`SPEC-010` REQ-1009).

### 6. Жалобы и staff

- один сценарий `ReportCase` для web и CLI;
- закрытый payload по `report-case.md`;
- ограничение частоты, ключ идемпотентности и группировка;
- число жалоб не меняет lifecycle версии;
- staff-действия (`triage`, `block`, `hide`, `restore`, выдача и отзыв
  `author_verified`) требуют platform-staff allowlist (account id из
  конфигурации) и всегда пишут `AuditEvent` с основанием;
- полный RBAC и org-роли откладываются.

### 7. Audit

Существующий append-only `audit_event` расширяется закрытым набором строк
`action` для publish/grant/report/staff. Очистка payload наследует audit
helper в `apps/api`; секреты, токены приглашения, сырые подписи attestation
и тела писем не сохраняются.

### 8. Что сознательно не входит

- CLI-команды publish/report/grant (`P8-C2`);
- web-экраны своих объектов и прав (фаза 9 / `#183`);
- автоматическое слияние локального реестра и CRDT;
- удалённое отключение установленных целей (`ADR-0032`);
- платежи, org SSO, доступ по ссылке без адресата;
- брокер Temporal / Celery / Redis;
- переписывание исторических байтов `ValidationSnapshot` при ужесточении
  политики.

## Последствия

- появляется `SPEC-026` с исполнимыми требованиями серверной материализации
  `#181`;
- `SPEC-018` расширяет закрытый реестр `JobType`;
- `SPEC-020` перестаёт исключать таблицы прав, жалоб и планов публикации из
  будущего дерева миграций — их авторствует `#181` в том же Alembic tree;
- `packages/contracts` и OpenAPI получают аддитивные маршруты и схемы до
  обработчиков;
- worker-обработчики перестают быть чистыми заглушками для validation,
  publish, eligibility и invite;
- эксплуатация получает метрики глубины очереди, retry и dead_letter по
  новым типам (`docs/operations/observability.md`);
- продуктовые `SPEC-002`, `SPEC-007`, `SPEC-016` не дублируются:
  implementation SPEC ссылается на них.

## Условия пересмотра

Решение пересматривается, если:

- частота и разнообразие jobs превысят возможности Postgres-очереди
  (пересмотр `ADR-0038`);
- staff allowlist окажется недостаточен и потребуются роли или организации;
- Resend или почтовый транспорт потребуют отдельного compliance-контура;
- появится измеренная нужда в multi-step saga-оркестраторе вместо цепочки
  идемпотентных jobs.
