# ADR-0164: Portability is an evidence-bound claim, not an adaptation

Status: accepted.

## Context

A component owner may maintain native projections for Codex and Pi but believe
the logical source can be transformed for Claude Code. Requiring every owner to
operate every harness blocks useful publication. Treating the component as
universally installable creates the opposite problem: no exact target bytes,
provider surface, limitations, or safety result exists to justify installation.

The word `portable` is already used by authoring for common source. Source
portability does not establish target compatibility.

## Options

1. Require an exact published adaptation for every installation and offer no
   exception. This is safe but prevents informed local experimentation.
2. Add a wildcard adaptation or `universal=true`. This gives future and unknown
   harnesses support without target evidence.
3. Keep exact adaptation as the normal path, add an immutable bounded author
   claim, and permit a separately consented local materialization workflow.

## Decision

Option 3 is accepted.

A **portability claim** is immutable content of a component version. It binds the
exact common-source artifact digest, an explicit non-empty set of canonical
target harness IDs, an allowed deterministic transform family/version, claimed
component types and scopes, declared prerequisites and semantic limitations,
evidence references, issuer, issue time, and optional expiry. `all`, wildcard,
unknown, and future harness values are invalid. Changing the claim creates a new
component version.

A claim is an author assertion. It does not create an adaptation, technical
support declaration, assessment, recommendation, `component_verified`, setup
compatibility, or install eligibility. Catalog search treats exact availability
and claimed portability as separate predicates. Exact is the default; claim-only
results require an explicit compatibility mode and carry their match reason.

Normal public setup publication still requires an exact published adaptation
for the setup harness. A portability claim cannot close a public setup graph.

Risk installation is consumer-owned and local. CLI work in GitHub issues #149
and #150 must:

1. pin the component version, source artifact, target harness, provider profile,
   transform, and target scope;
2. deterministically materialize exact target projection bytes;
3. validate structure and run required safety and compatibility checks on those
   bytes;
4. disclose permissions, semantic losses, missing evidence, and limitations;
5. bind consent to the complete result and preconditions;
6. record a local immutable adaptation and personal setup/overlay before normal
   bundle assembly.

Consent may cover an unverified or stale assessment and declared semantic loss.
It cannot override digest mismatch, unsafe archive/path behavior, secret
exposure, an unsupported provider surface, ownership collision, or changed
target precondition. Any bound-value change makes the plan and consent stale.

The platform stores and presents the published claim and safe evidence links. It
does not execute transforms, receive local generated bytes through catalog read,
or silently convert a claim into an exact adaptation.

## Consequences

- Owners can communicate bounded portability without pretending to maintain
  every projection.
- Users can experiment through an explicit recoverable path.
- Search can answer both “works exactly” and “owner claims it can be adapted”
  without merging them.
- Generated local adaptations do not pollute the public component version or
  its statistics.

## Revisit conditions

Revisit if platform-hosted transformation becomes an explicitly authorized
publication service, or if a multi-harness signed projection format removes the
need for target materialization.
