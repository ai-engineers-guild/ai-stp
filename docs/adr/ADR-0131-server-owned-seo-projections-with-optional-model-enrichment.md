# ADR-0131: SEO является серверной проекцией, модель — необязательным редактором

Статус: предложено. Уточняет `ADR-0022`, `ADR-0038`, `ADR-0076`, `ADR-0088`,
`ADR-0089` и `ADR-0095`.

## Контекст

Публичный каталог уже имеет серверные страницы компонентов, сетапов, сервисов и
стран, а repository content hub — страницы статей. Статьи получают собственные
metadata и JSON-LD, но sitemap перечисляет только статические маршруты и статьи;
остальные публичные сущности наследуют общую metadata и не образуют полного
поискового контура. Создание сервиса изменяет mutable catalog metadata, а статья
становится доступной только в составе нового web image, поэтому у этих двух
источников нет общего события публикации.

SEO-представление зависит одновременно от immutable опубликованных данных и от
mutable публичных связей: профиля автора, внешних сервисов, стран, media и
актуального состояния доступности. Запись SEO-полей в паспорт изменила бы digest
без изменения устанавливаемого объекта; построение всех полей на каждом web
request сделало бы результат нестабильным и неаудируемым.

`ADR-0022` запрещает `ai_stp` вызывать интерфейс модели, чтобы локальный CLI,
паспорта, подбор, validation и установка не зависели от ключа, счёта, сети и
недетерминированного ответа. Для публичной редакторской проекции существует иная
граница: сервер уже работает асинхронно и может деградировать до механически
полного результата без влияния на доверие и пригодность объекта.

## Варианты

1. **Строить metadata только в Next.js из текущего API-ответа.** Малый diff, но
   sitemap, OG, LLM-документы и HTML начнут повторять правила, а результат нельзя
   связать с exact набором исходных фактов.
2. **Хранить SEO-поля в паспорте или article Markdown.** Автору понятна форма, но
   presentation смешивается с immutable domain identity, а сервисы и производные
   региональные страницы всё равно остаются без общего механизма.
3. **Блокировать публикацию синхронным вызовом модели.** Сразу даёт один вариант
   текста, но доступность и корректность каталога становятся зависимы от внешней
   недетерминированной системы.
4. **Материализовать детерминированную серверную проекцию и улучшать её
   необязательным фоновым вызовом модели.** Принято: каждый объект сразу получает
   корректную страницу, а AI-результат включается только после проверки и
   атомарной смены активной ревизии.

## Решение

Платформа хранит immutable `SeoFactSnapshot` и `SeoRevision`, а указатель
`SeoActiveRevision` выбирает одну активную ревизию для пары subject/locale.
Subject имеет закрытый вид `component`, `setup`, `article`, `service` или
`country`. Snapshot содержит только публичные факты и их общий digest; SEO не
изменяет паспорт, доверие, lifecycle или исходную статью.

Каждое событие публикации или изменение публичных фактов транзакционно ставит
идемпотентное `seo_build` в существующую PostgreSQL-очередь. Handler сначала
создаёт и активирует детерминированную base-ревизию. Недоступность любого
model-serving контура не задерживает этот переход и не меняет индексируемость.

После base-ревизии опционально ставится `seo_enrich`. Worker вызывает один
OpenAI-compatible endpoint LiteLLM; выбор модели, fallback и upstream CLIPROXY
принадлежат LiteLLM. В job, snapshot, лог и базу не попадают credential или
полный model prompt. Ответ принимается только по закрытой JSON Schema, проходит
проверку длины, URL, языка, происхождения утверждений, секретов и точного
`source_digest`, после чего новая ревизия активируется одной транзакцией.

Таким образом уточняется `ADR-0022`: CLI, agent-facing core, паспорта, подбор,
validation, публикация доменного объекта и установка по-прежнему не вызывают модель
и не требуют model credential. Только серверное улучшение presentation после
готовой base-ревизии может обратиться к операторскому LiteLLM; выключение этого
контура оставляет всю продуктовую функцию, кроме редакторского улучшения текста.

Web, sitemap, Open Graph image, JSON-LD и LLM-документы читают одну активную
SEO-ревизию. Sitemap и LLM-индексы являются кэшируемыми проекциями, а не файлами,
которые дописывает каждый job. Их generation меняется при активации ревизии;
immutable OG asset адресуется revision ID.

Article authoring, repository import, staff publication и active serving
принадлежат `ADR-0132`; SEO получает exact active `ArticleRevision` и не меняет
её lifecycle или body. Сервис остаётся отдельной от passport catalog metadata по
`ADR-0088`, но индексируемость требует публичного описания и проверяемого source
URL, а каждое изменение его агрегата создаёт новый SEO snapshot.

## Последствия

- Появляется новая серверная доменная проекция и два типа job; внешний брокер и
  отдельный SEO-service не нужны.
- `LiteLLM` и `CLIPROXY` разворачиваются отдельным optional compose profile и не
  входят в dependency closure CLI или обязательный startup API/worker.
- Повторная доставка безопасна по subject, locale, исходному digest, template и
  prompt version; устаревший model response сохраняется как `stale`, но не
  активируется.
- Ответ модели никогда не является evidence и не может задать canonical,
  lifecycle, trust, verification или `index_eligible`.
- Rollback отключает enrichment и возвращает указатель на последнюю base-ревизию;
  удаление новых таблиц до окончания окна совместимости запрещено.
- Смена template, prompt или модели не меняет domain object; явный rebuild создаёт
  новую SEO-ревизию того же snapshot.

## Условия пересмотра

- Детерминированный base-профиль измеримо не позволяет публиковать полезную
  страницу без модели.
- Объём sitemap превышает предел одного файла или generation становится дорогим;
  тогда меняется только стратегия shard/cache.
- Появляется несколько независимых потребителей domain events; тогда повторно
  оценивается PostgreSQL queue против outbox relay/broker.
- Model enrichment начинает влиять на доменную публикацию, validation или trust;
  это требует отдельного решения и не является расширением этого ADR.
