# ADR-0128: HTTP-лимитер одного узла — два скользящих окна в процессе

Статус: принято. Уточняет `SPEC-010` `REQ-1015`.

## Контекст

Публичный `/v1` уже отклоняет избыток запросов кодом `AI_STP_RATE_LIMITED` и
заголовком `Retry-After`. Политика была одной: 120 запросов за 60 секунд на
тройку HTTP-метода, шаблона маршрута и транспортного адреса. Это не даёт
общего потолка на процесс и не даёт часового бюджета на адрес: один клиент
на многих шаблонах проходит, а сто клиентов на одном шаблоне делят один
карман.

Нужны два независимых бюджета MVP: не более 100 запросов в минуту на весь
узел и не более 1000 запросов в час с одного транспортного адреса. Оператор
должен задавать оба числа и оба окна без выпуска нового кода. Отсутствие
переменных не может снова стать безлимитом: `maximum=0` в уже существующем
`SlidingWindowLimiter` пропускает всё.

`SPEC-010` по-прежнему исключает Redis из MVP. Топология `ADR-0040` держит
Caddy единственной публичной точкой, а uvicorn не включает
`proxy-headers`: `request.client.host` сегодня — сосед (Caddy или `web`),
а не публичный клиент.

## Варианты

1. **SlowAPI** с `application_limits` (общий бюджет) и `default_limits`
   (на `key_func`, обычно IP). Документированная модель ровно двух карманов;
   in-memory backend — для одного процесса. Отвергнуто: новая зависимость,
   отдельный error path вместо уже существующего конверта, Redis в
   документации появляется сразу при втором воркере — а второй воркер
   `SPEC-010` и так не обещает.
2. **fastapi-limiter / Redis.** Точный счётчик на несколько реплик.
   Отвергнуто: Redis вне границ MVP, а деплой один процесс API.
3. **`rate_limit` Caddy или отдельный прокси-контейнер.** Лимит на входе
   в контур. Отвергнуто для MVP: второй механизм, второй набор чисел, и
   отказ больше не проходит через конверт `AI_STP_RATE_LIMITED`.
4. **Два скользящих окна на уже существующем in-process лимитере.**
   Принято. Алгоритм, вытеснение ключей и инъекция `now=` уже в дереве;
   меняется только то, *что* считается.

## Решение

HTTP-ворота процесса API — два независимых скользящих окна перед
обработчиком маршрута:

- общее окно процесса, ключ один на все запросы, по умолчанию 100 за 60 с;
- окно транспортного пира (`request.client.host`, иначе `unknown`), по
  умолчанию 1000 за 3600 с.

Оба лимита и оба окна задаются env
(`AI_STP_API_RATE_LIMIT_OVERALL_*`, `AI_STP_API_RATE_LIMIT_IP_*`).
Отсутствие переменных оставляет эти значения. Явное `0` отключает только
это измерение. Проверка обоих окон идёт до записи в любое: отказ не
расходует второй бюджет. Метод и шаблон маршрута в ключ не входят — старая
политика 120/маршрут/минуту заменяется, а не складывается. Заголовки
`X-Forwarded-For` и `Forwarded` не являются адресом, пока нет отдельного
решения о доверенном прокси. Код ошибки и зависимость не меняются: `429`,
`AI_STP_RATE_LIMITED`, `Retry-After` по окну, которое отказало.

## Последствия

- `REQ-1015`, `docs/contracts/http-api.md` и
  `docs/operations/production-readiness.md` называют те же числа.
- Старые `AI_STP_API_RATE_LIMIT_REQUESTS` /
  `AI_STP_API_RATE_LIMIT_WINDOW_SECONDS` больше не читаются: `extra=ignore`
  на настройках сервиса, чтобы прежний `0` не открыл публичный API.
- Пока uvicorn без `proxy-headers`, «один IP» — пир Caddy/`web`. Это
  ограничение решения, а не скрытый `X-Forwarded-For`.
- 100 запросов в минуту на весь процесс жёстче прежних 120 на шаблон:
  health, веб SSR и CLI делят один карман. Исключений маршрутов нет, пока
  измерение не покажет, что пробы сами исчерпывают бюджет.
- Второй воркер или вторая реплика снова делают in-memory счётчик
  локальным; это уже было правдой и остаётся причиной пересмотра.

## Условия пересмотра

- Появилась вторая реплика или несколько воркеров uvicorn на один бюджет.
- Принято решение доверять hop-by-hop идентификатору за Caddy
  (`Forwarded` / `X-Forwarded-For` только от названного прокси).
- Пробы готовности сами упираются в общий бюджет на развёрнутой среде.
- Понадобился отдельный класс политики на вход, жалобу или запись.
