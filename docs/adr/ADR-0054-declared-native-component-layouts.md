# ADR-0054: Декларативные native-layouts компонентов

Статус: принято.

## Контекст

Обнаружение нативных компонентов покрывало Claude Code и часть Codex, хотя MVP
объявляет пять харнессов. Обход неизвестных каталогов был бы шире явного
контракта и неизбежно классифицировал бы пользовательские файлы по догадке.
Одновременно один путь может быть совместим с несколькими харнессами, поэтому
повтор одной находки под несколькими `harness_id` сделал бы последующее принятие
по пути неоднозначным.

Codex, Pi, OpenCode и Grok Build также поддерживают перемещаемые корни и общие
каталоги `.agents`. Корень харнесса нельзя вычислять из названия продукта или
заменять общим соглашением.

## Решение

CLI содержит закрытую таблицу layout-правил. Каждое правило объявляет вид
компонента, форму пути, область, владельца-harness и ссылку на официальную
документацию. Глобальный путь строится либо от документированного config root
харнесса, включая его environment override, либо от home для общей конвенции
`.agents`. Проектные правила строятся только от явно переданного project root.

Один общий путь выдаётся один раз с `harness_id=null`, а не копируется для всех
совместимых потребителей. Результат имеет `layout_source` и `candidate_id`.
`candidate_id` — доменный хэш канонического набора `component_type`, `harness_id`,
`scope`, отредактированного `source_path` и `layout_source` в области
`ai-stp:native-discovery:v1`. Он стабилен для одной находки и не является
устойчивым логическим `Component.stable_id`: последний появляется только после
явного `component adopt`.

Discovery читает только directory entries и метаданные файлов, сортирует полный
результат детерминированно, не открывает содержимое и ничего не пишет. Новый
харнесс или новый layout добавляется только вместе с официальным источником и
исполняемой фикстурой.

## Последствия

- Claude Code, Codex, Pi, OpenCode и Grok Build имеют проверяемое глобальное и
  проектное покрытие без сканирования home;
- `PI_CODING_AGENT_DIR`, `OPENCODE_CONFIG_DIR`, `GROK_HOME` и `CODEX_HOME`
  одинаково управляют survey и component discovery;
- агент может ссылаться на устойчивый `candidate_id` и показать происхождение
  классификации, но для принятия по-прежнему передаёт точный путь;
- package-, marketplace- и GitHub-происхождение не выводится из расположения на
  диске и требует отдельного source adapter;
- совместимые пути не приписываются случайному харнессу.

## Условия пересмотра

Решение пересматривается при несовместимом изменении layout официальным
харнессом, появлении versioned layout manifest или необходимости адресовать одну
физическую находку несколькими независимыми вариантами без неоднозначного adopt.
