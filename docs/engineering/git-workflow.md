# Git workflow

## Ветки

`main` — единственная линия репозитория: ветка по умолчанию, интеграционная и выпускная одновременно. В неё направляются PR с реализацией. Отдельной интеграционной ветки нет.

Так было не всегда: `dev` существовал как интеграционная ветка, и переход из него в `main` требовал отдельного продвижения с двойным ревью. Этот шаг ничего не ловил — `main` не защищён, обязательных проверок нет, а продвижение накапливалось неделями и уходило одним PR из сотен коммитов. Второй контур ветки стоил дороже, чем давал, и снят.

Работа ведётся в личных ветках участников:

- `rldyourmnd` — личная рабочая ветка Danil, владельца проекта;
- `letya999` — личная рабочая ветка Артёма.

Каждый участник пишет только в свою личную ветку и поддерживает её свежей, вливая в неё `main`. Готовое изменение уходит PR из личной ветки в `main`; после зелёного CI на точном HEAD автор сливает его merge-коммитом. Интеграцию участники выполняют совместно — каждый свою работу.

Когда CI недоступен, доказательством служит полный `just check`, прогнанный на
точном HEAD, а его вывод — выполненные команды, число тестов, покрытие —
записывается в сообщение merge-коммита. Это замена доказательства, а не отмена
требования: слить без прогона вообще нельзя ни в каком случае. Правило записано
здесь потому, что раннер уже был недоступен и мержи шли именно так; молчаливое
расхождение практики с правилом хуже обоих вариантов.

Слить чужой PR может владелец проекта, когда автор иначе остаётся
заблокированным. Тогда конфликты разбирает тот, кто сливает, а не автор.

После слияния PR GitHub автоматически удаляет ветку на origin; личная ветка живёт дальше локально — влей в неё свежий `main` и опубликуй снова обычным push. Отключение автоудаления требует прав администратора репозитория.

```text
rldyourmnd (Danil)      letya999 (Артём)
        \                   /
      PR в main после зелёного CI
                ↓
               main
```

Личные ветки не являются интеграционным источником истины: изменение попадает в продукт только слиянием в `main`.

Участников репозитория несколько, и это не противоречит продуктовой модели одного пользователя из `docs/product/vision.md`: там речь о том, для кого сделан продукт, здесь — о тех, кто его пишет.

Заметное изменение начинается с чернового PR из личной ветки в `main`, чтобы направление было видно рано. Принудительная перезапись истории `main` и удаление ветки запрещены соглашением участников; платформа это сейчас не обеспечивает, причина указана в `quality-gates.md`.

Запрет перезаписи истории относится к `main`. Личная ветка принадлежит своему владельцу: он вправе перестроить её и опубликовать заново, но чужую личную ветку не трогает никто.

### `.gds/compiled-policy.json` не является правилом этого репозитория

Файл — проекция внешнего control plane, а не источник истины для участников. Он помечает часть настроек GitHub как `managed`, но здесь ничто их не применяет и не проверяет расхождение, и наблюдаемые значения репозитория от объявленных отличаются — в частности по разрешённым способам слияния.

Способ слияния задаёт настоящий документ. Проекция его не отменяет. Пока проекция не применяется чем-то, что действительно пишет настройки и проверяет drift, она остаётся справочным снимком, и ссылаться на неё как на действующее правило нельзя.

## Коммиты

Допустимые типы:

- `docs`;
- `feat`;
- `fix`;
- `refactor`;
- `test`;
- `chore`;
- `perf`.

Коммит атомарен по одной причине. Генерируемые результаты и их источник изменяются вместе, кроме отдельно проверяемого коммита продвижения версии или артефакта.

Индексируются только явно перечисленные пути. Общая команда добавления всего рабочего дерева запрещена: инструменты агентов пишут во вложенные служебные каталоги в течение сессии, и неограниченное добавление собирает в коммит посторонние файлы.

## Pull request

Описание PR содержит:

- цель и границы;
- затронутые спецификации, ADR, схемы и публичные контракты;
- точные базовый и конечный SHA;
- миграцию, совместимость и порядок слияния;
- выполненные команды и наблюдаемые результаты;
- проверки, которые не запускались;
- способ возврата;
- межрепозиторный порядок;
- остаточные риски;
- влияние на документацию.

После последней правки проверки запускаются заново. Успешный запуск на другом SHA не является доказательством текущего PR. Требуется независимая проверка; изменение после неё делает прежнее одобрение устаревшим.

## Последовательные PR

Для линейного стека каждый PR основан на ветке предыдущего. Пока стек не слит, используется merge-коммит, сохраняющий происхождение:

```text
слить нижний PR в main
→ сохранить его ветку до посадки дочернего PR
→ перенаправить следующий PR на main
→ проверить новый совокупный diff
→ повторить CI и review
```

При использовании squash или rebase каждый дочерний PR пересобирается на новом `main`, получает новый CI и новую проверку; прежние результаты не переносятся.

## Исправление идёт вперёд

Ошибка в `main` исправляется следующим PR, а не перезаписью истории и не откатом ветки. Второго контура, который поймал бы её раньше, больше нет — это осознанный размен из `ADR-0084`, и цена его в том, что скорость реакции важнее аккуратности отката.

Выпуск не является следствием слияния: он выполняется отдельной операцией с собственным разрешением владельца.

## Межрепозиторные изменения

Не смешивать в одном слиянии:

- изменение реализации провайдера;
- закрытые проверки харнессов;
- выпуск артефакта провайдера;
- продвижение закреплённой версии в `nddev-harnesses`;
- продвижение манифеста провайдера в `ai_stp`.

Порядок и окно совместимости описываются в PR. Каждый репозиторий получает отдельный PR и собственные проверки.
