# Публикация первопартийного корпуса запуска

Операторский batch читает неизменяемый снимок `ai_stp_contracts.first_party` и
проводит каждый объект через уже существующие аутентифицированные маршруты
`publication plan` → привязка точных байтов → подтверждение точного hash →
серверная валидация → публикация. Он не пишет каталог напрямую, не вызывает
`catalog_seed` и не меняет validation policy, `component_verified` или trust
lane. Experimental seed из `SPEC-021` остаётся отдельным fixture/demo-путём.

Фактическая внешняя публикация — отдельное решение оператора. Сам инструмент
только возобновляет обычную последовательность и собирает отчёт.

## Предусловия

1. Войти владельцем платформенного пространства имён и активным устройством:
   `auth login --provider github --json`.
2. Убедиться, что обязательные доказательства по политике проверок уже
   подготовлены тем же путём, что и для любой публикации. First-party
   происхождение не даёт исключений.
3. Держать файл состояния вне checkout.

## Review

Review сохраняет точный digest корпуса, координаты объектов, `plan_id`,
`plan_hash`, ключи идемпотентности и blockers. Планы создаются для всех
объектов; компоненты идут раньше зависимых сетапов.

```text
python apps/cli/tools/first_party_launch_publication.py review \
  --state /secure/ai-stp/first-party-launch.json
```

Повтор с тем же digest возобновляет сохранённые ключи и не создаёт второй план.

## Apply

Apply требует явного `--confirm` и тот же `corpus_digest`, который вернул
review. Он читает публичный каталог: совпадающий digest той же `X.Y` пропускает
объект как уже опубликованный, другой digest блокирует по `REQ-2606` и не
вызывает confirm. Неопубликованные объекты привязывают точные байты, подтверждают
сохранённый plan и читают status, пока состояние не станет `published` либо
отказным. Сетап подтверждается только после `published` всех его точных
component pins. Любой blocker останавливает зависимые объекты.

`--max-polls` задаёт верхнюю границу ожидания одного plan (по умолчанию 180
секунд). Validate с safety scan на проде занимает десятки секунд; слишком короткое
ожидание помечает живой plan как blocker и оставляет job в очереди.

```text
python apps/cli/tools/first_party_launch_publication.py apply \
  --state /secure/ai-stp/first-party-launch.json \
  --corpus-digest sha256:<reviewed-digest> \
  --confirm
```

Прерванный запуск повторяют той же командой: status читается раньше повторного
confirm, ключи идемпотентности не меняются.

## Status

```text
python apps/cli/tools/first_party_launch_publication.py status \
  --state /secure/ai-stp/first-party-launch.json
```

Read-only обновление сохранённых `plan_id`. Если ответ confirm потерян, сначала
читают status, а не создают новый plan.

## Отказ

- Другой digest корпуса, другой владелец или устройство — остановка.
- Отсутствующее обязательное доказательство — blocker; зависимый сетап не
  подтверждается.
- Другие байты под тем же `X.Y` отклоняет сервер по `REQ-2606`.
- Seed, прямая запись каталога и обход validation policy запрещены.
