# SPEC-005: Реестр, варианты и версии объектов

## Цель

Локальный и облачный реестры однозначно идентифицируют компоненты и сетапы, сохраняют закрытые черновики и публикуют неизменяемые версии для конкретных харнессов с точным происхождением.

## Границы

Входят устойчивые идентификаторы, нативные реализации компонентов, версии `X.Y`, доступ к основной линии, закрытые черновики, теги, публичность и состояния жизненного цикла. Платежи, выплаты и изменение опубликованных байтов не входят в MVP.

## Термины

- `Component` и `Setup` — устойчивые логические сущности.
- `ComponentVariant` — нативная реализация компонента для одного харнесса.
- `SetupLineage` — необязательная связь происхождения между сетапами разных харнессов.
- `DraftRevision` — изменяемая закрытая история до фиксации.
- `PublishedVersion` — неизменяемый снимок с точным хэшем.

## Требования

- `REQ-501`: Компонент и сетап имеют устойчивый логический идентификатор, независимый от локального пути.
- `REQ-502`: Сетап принадлежит ровно одному харнессу, заданному при создании и неизменяемому; нативная реализация остаётся свойством компонента, а не сетапа.
- `REQ-503`: Опубликованная версия имеет формат `X.Y` и неизменяемые байты, паспорт версии и точные ссылки на зависимости; отдельной сущности манифеста не существует.
- `REQ-504`: Один номер версии нельзя повторно использовать для другого хэша.
- `REQ-505`: `SetupVersion` закрепляет точные `ComponentVersion` и, если у компонента есть нативные реализации, их идентификаторы.
- `REQ-506`: Любое изменение состава, точной ссылки или материализованной накладки создаёт следующую младшую версию сетапа автоматически.
- `REQ-507`: Переход на новую основную линию требует явного решения пользователя и создаёт отдельную границу доступа.
- `REQ-508`: Публичная версия компонента и сетапа происходит из публичного репозитория GitHub, точного коммита и подпути; закрытый черновик может происходить из локального артефакта с хэшем.
- `REQ-509`: Неполный черновик может синхронизироваться приватно, но не регистрируется, не ранжируется и не появляется в поиске.
- `REQ-510`: `component_type` принимает ровно восемь значений: `instruction`, `skill`, `mcp`, `hook`, `command`, `agent`, `plugin`, `setting`.
- `REQ-511`: Зависимости разделены на `requires_components` с точными ссылками на версии и `requires_capabilities` из закрытого версионируемого словаря.
- `REQ-512`: Нативная упаковка объявляется отдельным закрытым словарём `projection_kind` и не смешивается с `component_type`.
- `REQ-513`: Публикуемая версия имеет непустой список тегов, каждый из которых принадлежит закрытому версионируемому словарю; форма, нормализация и предел принадлежат `docs/contracts/tag-vocabulary.md`.
- `REQ-514`: Проект закрепляет для каждого используемого харнесса ровно один сетап, ровно одну выбранную версию и не более одной установленной; вне окна ожидающей установки они совпадают, а каналы выпуска и несколько одновременно действующих версий одного сетапа не поддерживаются.
- `REQ-515`: Родство сетапов разных харнессов выражается ссылками происхождения и не создаёт общий номер версии, общую неизменяемость и общее право доступа.
- `REQ-516`: Продуктового предела на число компонентов в сетапе нет; отказ возникает только из конфликта, несовместимости или предела ресурсов.
- `REQ-517`: CLI обнаруживает компоненты в объявленных глобальных и проектных layout всех семи поддерживаемых харнессов, установленные глобальные GitHub-компоненты из поддерживаемых manifest-источников и MCP server packages из bounded package manifest и точного entry point, классифицирует вид, native role, harness и область, показывает путь, layout, transport capabilities и source evidence и выдаёт воспроизводимый идентификатор кандидата, отдельный от логического идентификатора Component.
- `REQ-518`: Обнаружение отделено от принятия: ничего не импортируется и не регистрируется без явного действия пользователя, значения секретов не читаются, а metadata adapter ограничен объявленными файлами и размером и возвращает безопасную диагностику вместо догадки.
- `REQ-519`: Принятие компонента создаёт узкий паспорт в локальном реестре из allowlist наблюдённых фактов и exact bytes; оно не изменяет найденный объект и не требует аккаунта. Явный sidecar import, если он выбран пользователем, остаётся отдельным входным путём.
- `REQ-520`: Репозиторий, где рядом находятся код проекта и компоненты, поддерживается: компонент имеет собственный корень, отличный от корня проекта.
- `REQ-521`: Форк доступного объекта создаёт новый устойчивый идентификатор с получателем как владельцем и закрытым режимом по умолчанию, записывает происхождение и может синхронизироваться в приватный облачный реестр получателя; оригинал при этом не изменяется.
- `REQ-522`: Неизменённый клон чужого объекта не публикуется под новым пространством имён; публикация производного сетапа требует содержательного изменения состава, паспорта или байтов включённого компонента и полной проверки.
- `REQ-523`: Публикация производного компонента требует изменённых байтов или паспорта и новой идентичности и версии в пространстве имён получателя.
- `REQ-524`: Публичная производная публикация допустима, только когда каждый включённый байт и ссылка публичны или принадлежат получателю, а применимые лицензии разрешают распространение; неизвестное право распространения закрывается отказом.
- `REQ-525`: Владелец или его Agent может обогатить локальный component draft закрытым patch относительно exact current revision. Каждое подтверждённое изменение создаёт content-addressed child revision; stale revision, secret-bearing field и неизвестное поле отклоняются. Локальная проверка публикационной полноты перечисляет все отсутствующие и неверные поля и не выдаёт облачного разрешения.
- `REQ-526`: CLI отдельно разбирает опубликованное краткое имя, сокращение или URL GitHub, локальный путь и URL коллекции в ограниченное намерение источника без утверждения о доверии. Только отдельное разрешение намерения GitHub с полным commit SHA создаёт `github/exact`; ветка, тег, URL с учётными данными и небезопасный подпуть не получают точное происхождение.
- `REQ-527`: Одна исполнимая таблица владеет идентификатором, уровнем поддержки, detection root, глобальными и проектными layout, проекционными возможностями и известными пробелами Claude Code, Codex, Pi, OpenCode, Grok Build, Cursor, Antigravity и общей строки `undefined`; discovery и survey строятся из неё.
- `REQ-528`: CLI создаёт безопасный переносимый authoring template для каждого из восьми видов компонентов и детерминированно проецирует его для одного конкретного харнесса. Условные блоки привязаны к закрытому реестру харнессов, path-placeholder принимает только ограниченный относительный POSIX path, неизвестный или неоднозначный синтаксис отклоняется до публикации; теги внутри fenced code остаются буквальным текстом.
- `REQ-529`: В явно названном корне CLI ограниченно читает `nori.json` и askill/Vercel-compatible `.agents/.skill-lock.json` версии 3 как внешние metadata ports. Объявленные компоненты и exact folder digest становятся только наблюдаемыми фактами локального draft; repository, commit, доверие и публикационная готовность не выводятся из внешнего заявления. Import не исполняет script, Git, package manager и сетевой запрос.
- `REQ-530`: Раскладка вправе объявить ключ, под которым харнесс держит клиентские MCP внутри файла, объявленного также как `setting`. Такой файл становится находкой `mcp` только при наличии хотя бы одного объявленного сервера, и находка `setting` при этом сохраняется. Читаются только имена серверов и попадают в `evidence_refs`; значения рядом с ними не читаются. Файл без ключа, с пустым объявлением, повреждённый или превышающий предел размера находок не даёт. Харнесс без документированной раскладки объявляет проверенный пробел вместо неё.

## Состояния и ошибки

Черновик имеет состояния `incomplete`, `valid`, `conflict` и `frozen`. Опубликованная версия имеет состояния `active`, `deprecated`, `blocked` и `hidden`; состояние жизненного цикла не меняет байты.

Версия в состоянии `deprecated` остаётся доступной и устанавливаемой, а поиск и состояние показывают предупреждение и доступную замену. Версия в состоянии `blocked` запрещает новые установки и обновления, но уже установленная цель не отключается и не удаляется автоматически; пользователь получает заметное предупреждение с причиной и безопасным следующим шагом, если они опубликованы. Автономно используется последнее известное состояние с указанием времени проверки.

Независимо от ручного состояния версия, потерявшая актуальные обязательные доказательства, блокируется для новых установок и обновлений по правилу пригодности `SPEC-007`; ручное `blocked` остаётся отдельным действием поверх этого правила.

Ошибки различают повтор версии, несовпадение хэша, отсутствующую зависимость, неверное происхождение, пустые теги и запрещённое распространение.

## Безопасность и приватность

Закрытые байты не встраиваются в публичный производный объект. Лицензия и право доступа проверяются до материализации. Публичный артефакт не содержит локальные пути, секреты и неуправляемые файлы. Блокировка версии прекращает новые установки независимо от ранее выданного доступа.

## Совместимость и миграция

Младшие версии доступны владельцу основной линии; новая основная линия не открывается автоматически. Конфликт одновременного присвоения одного номера на двух автономных устройствах разрешается перевыпуском по `SPEC-009` REQ-912; опубликованный номер никогда не перемещается. Изменение схемы паспорта требует отчёта преобразования. Старый клиент читает известные поля и сохраняет неизвестные необязательные поля без перезаписи опубликованного снимка.

## Критерии приёмки

| Требование | Исполнимый способ проверки |
|---|---|
| `REQ-501` | Проверка свойств переносит объект между путями без смены устойчивого идентификатора. |
| `REQ-502` | Проверка схемы отклоняет сетап без `harness_id`, с несколькими значениями и с полем варианта. |
| `REQ-503` | Проверки мутаций доказывают неизменяемость опубликованных байтов и метаданных. |
| `REQ-504` | Ограничение уникальности отклоняет повтор `X.Y` с новым хэшем. |
| `REQ-505` | Эталонный паспорт версии сетапа содержит точные ссылки и хэши компонентов. |
| `REQ-506` | Определитель изменений предлагает следующую младшую версию и запрещает повтор номера. |
| `REQ-507` | План основной версии требует отдельного подтверждения пользователя. |
| `REQ-508` | Публикация без репозитория, коммита или подпути отклоняется; ветка, тег и `latest` отклоняются отдельно. |
| `REQ-509` | Поиск и ранжирование не видят неполный облачный черновик. |
| `REQ-510` | Проверка перечисления принимает ровно восемь значений и отклоняет `marketplace`. |
| `REQ-511` | Проверка схемы отклоняет требование окружения в `requires_components` и наоборот. |
| `REQ-512` | Проверка схемы отклоняет значение упаковки в `component_type` и значение вида в `projection_kind`. |
| `REQ-513` | Публикация с пустыми тегами, значением вне словаря, неверной формой или превышением предела отклоняется разными ошибками. |
| `REQ-514` | Фикстура проекта отклоняет второй сетап того же харнесса и вторую выбранную версию, а окно `pending_install` держит выбранную и установленную версии раздельно. |
| `REQ-515` | Изменение версии одного сетапа не меняет версию и доступ связанного сетапа. |
| `REQ-516` | Нагрузочная фикстура большого сетапа проходит, а отказ возникает только по конфликту или пределу ресурсов. |
| `REQ-526` | Табличный parser corpus покрывает все поддержанные формы и неоднозначные/credentialed/escaping входы; resolver принимает только полный SHA и не повышает local, collection или published intent. |
| `REQ-527` | Проверка таблицы требует восемь строк без повторных layout, непустые источники и проекции, сравнивает derived detector/discovery rules с compatibility oracle и проверяет полный машинный ответ `toolchain harness-capabilities`. |
| `REQ-528` | Табличная проверка создаёт шаблон каждого из восьми видов и сравнивает повторные проекции для семи конкретных харнессов; неизвестные, повторные и вложенные условия, unsafe path, symlink и превышение размера закрываются отказом, а теги внутри fenced code сохраняются буквально. |
| `REQ-529` | Фикстуры Nori skill, subagent и slash command и project/global lock версии 3 создают по одному observed candidate и локальный draft с evidence ref и exact folder digest, но без repository/commit claim; duplicate key, symlink, oversized, unsafe path, неизвестная версия и неточный digest дают безопасную диагностику, а canary script не запускается. |
| `REQ-530` | Фикстуры `config.toml`, `opencode.json` и `opencode.jsonc` с объявленными серверами дают находку `mcp` рядом с находкой `setting` и evidence ref на каждое имя; пустое объявление, отсутствие ключа, повреждённый и превышающий предел файл находок не дают; комментарии и висячие запятые JSONC разбираются; значение с токеном в выдачу не попадает; машинная таблица сообщает пробел для харнесса без документированной раскладки. |
| `REQ-517` | Фикстуры всех семи харнессов и общей `.agents`-области возвращают вид, harness, область, путь и layout-source; Claude GitHub marketplace и Pi Git cache fixtures возвращают exact repository, commit и package identity, loose/packed refs совпадают, а npm fixture остаётся `package/observed` без remote claim; Python и TypeScript MCP packages требуют SDK dependency, declared entry point и импорт SDK в точном source, различают stdio/HTTP и не классифицируют docs/tests/application hooks; повтор даёт тот же candidate id, а environment overrides ведут к перемещённым корням. |
| `REQ-518` | Снимок реестра после обнаружения не меняется; secret fixture не попадает в вывод; malformed, oversized, unknown-version manifest, credential URL и cache escape закрываются безопасной диагностикой без утечки содержимого. |
| `REQ-519` | Принятие без сети создаёт узкий allowlist-паспорт и регистрирует exact bytes без аккаунта и без изменения исходного объекта. |
| `REQ-520` | Фикстура смешанного репозитория различает корень проекта и корень компонента. |
| `REQ-521` | Форк получает новый идентификатор, владельца-получателя и закрытый режим, а снимок оригинала не меняется. |
| `REQ-522` | Публикация байтово идентичного клона отклоняется типизированной ошибкой, а производный сетап с содержательным изменением проходит только полную проверку. |
| `REQ-523` | Производный компонент без изменённых байтов и паспорта отклоняется, а с изменениями получает новую идентичность в пространстве имён получателя. |
| `REQ-524` | Фикстура с закрытым чужим байтом и фикстура с запрещающей лицензией блокируют публичную публикацию производного объекта. |
| `REQ-525` | Process-level сценарий проходит show/update/validate; stale expected revision, symlink/oversized patch, secret field и неполный exact source дают типизированные отказы, а выпущенная ранее версия продолжает ссылаться на прежнюю ревизию. |
