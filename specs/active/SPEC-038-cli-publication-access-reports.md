# SPEC-038: CLI-клиент публикации, прав доступа и жалоб

## Цель

Авторизованный CLI проводит агента через серверные сценарии Фазы 8, сохраняя
локальную сборку и редактор паспортов на клиенте, а решения о владении,
публикации и доступе — на платформе. Проводные формы принадлежат
`packages/contracts`; этот документ задаёт только клиентскую последовательность
и границу раскрытия данных.

## Границы

Входят команды создания, чтения и подтверждения publication plan, последующее
чтение объектов владельца, grants и report cases. Входят явное подтверждение,
идемпотентный повтор и восстановление после потерянного ответа через чтение
серверного состояния.

Не входят серверная машина состояний, фоновые задания, PostgreSQL, модерация,
веб-интерфейс, изменение локального паспорта во время публикации и отправка
байтов артефакта маршруту, который принимает только паспорт.

## Термины

- **Локальная выпущенная версия** — неизменяемая пара `stable_id` и `X.Y`,
  связанная с точной ревизией паспорта в SQLite-реестре.
- **Неопределённый результат** — транспорт завершился без контрактного ответа,
  поэтому клиент не утверждает, произошёл ли внешний эффект.

## Требования

- `REQ-3801`: `publication plan` принимает только точную локально выпущенную
  версию компонента, материализует из зафиксированной ревизии формальный
  `ComponentVersionPassport` и передаёт digest её артефакта. Текущая голова не
  подменяет ревизию выпущенной версии.
- `REQ-3810`: `setup publish plan` принимает точную локально выпущенную версию
  сетапа и создаёт по плану на каждый закреплённый компонент, который ещё не
  публичен, и на сам сетап. Уже публичный участник перечисляется с признаком
  `already_published` и не перепланируется. Публичность определяется ответом
  платформы, а не локальной `visibility`.
- `REQ-3811`: Набор возвращает `set_digest` над упорядоченным списком
  участников: роль, вид объекта, `stable_id`, версия, `plan_hash` и признак
  `already_published`. Состояние отдельного плана в digest не входит. Набор
  сохраняется локально, потому что `plan_id` не восстанавливается расчётом;
  повторный `plan` для той же версии сетапа заменяет открытый набор.
- `REQ-3812`: `setup publish confirm` требует точный `set_digest` и явный
  `--confirm`, подтверждает участников в порядке набора — компоненты, затем
  сетап — и останавливается на первом отказе. Набор переходит в `partial`,
  опубликованные участники остаются опубликованными, а повторный `plan`
  перечисляет их как `already_published`. Набор, принадлежащий другому аккаунту
  или устройству, отклоняется.
- `REQ-3802`: Создание плана не публикует объект. Ответ показывает неизменяемые
  `plan_id`, `plan_hash`, срок и effects; подтверждение является отдельной
  командой с точным hash и обязательным `--confirm`.
- `REQ-3803`: Один сетевой вызов изменяющей команды сохраняет один ключ
  идемпотентности на всех транспортных повторах. После неопределённого результата
  confirm следующий безопасный шаг — `publication status`, а не новый эффект.
- `REQ-3804`: Все команды требуют активную cloud session и передают bearer token
  только проверенному HTTPS endpoint. JSON-ответы и ошибки не содержат токены,
  подписи, исходные байты или значения credentials.
- `REQ-3805`: Клиент grants и reports использует закрытые проводные модели,
  разделяет preview и confirm там, где этого требует серверный контракт, и не
  воспроизводит серверную матрицу полномочий локальными догадками.
- `REQ-3806`: Изменяющая команда grants требует явного подтверждения и
  стабильного ключа идемпотентности. Raw invitation token принимается только из
  названной переменной окружения и не попадает в аргументы процесса, URL,
  результат или ошибку.
- `REQ-3807`: Жалоба сначала сохраняется как exact локальный preview. Confirm
  принимает его идентификатор и digest, а повтор после неопределённого
  результата использует сохранённый payload и тот же ключ идемпотентности.
  Diagnostics являются необязательным bounded UTF-8 input, целиком видимым в
  preview и отклоняемым при наличии абсолютных путей или secret-bearing
  assignments.
- `REQ-3808`: Owner reads используют только авторизованные серверные list,
  object-detail и exact-version модели. CLI не считает grant владением, не
  смешивает owner workspace с локальным или публичным каталогом и возвращает
  opaque cursor без интерпретации.
- `REQ-3809`: `attestation sign` создаёт новый owner-only файл полного
  `AuthorAttestation`, подписывает ключом активного устройства точный digest
  выпущенного объекта и всех координат проверки и никогда не перезаписывает
  существующий файл. `publication plan` принимает такие файлы явно, до HTTP
  проверяет закрытую модель, точные `stable_id`, `version`, digest объекта и
  паспорта, аккаунт, устройство, отсутствие дублей и подпись, после чего
  передаёт только поля существующей проводной модели.

## Состояния и ошибки

Состояния publication plan приходят только из `PublicationPlanResponse` и не
вычисляются клиентом. Отсутствующая сессия и истёкшая сессия требуют нового
входа; отозванное устройство остаётся отдельным постоянным отказом. Ошибка
локальной полноты паспорта возникает до HTTP-вызова. После транспортной ошибки
confirm команда предлагает read-only status известного плана.

## Безопасность и приватность

Клиент материализует закрытую модель version passport и не добавляет к ней
содержимое артефакта или состояние окружения. Endpoint проходит общую проверку
HTTPS; redirect запрещён, чтобы bearer token не ушёл другому authority. Ошибки
не повторяют URL, токен или тело ответа.

## Совместимость и миграция

Новые команды аддитивны и используют существующий `/v1` и экспортированные
схемы. Локальный exact report preview хранится в отдельной таблице, добавленной
обычной обратимой миграцией SQLite; старые реестры сохраняют все существующие
строки. Версия, не связанная с доступной ревизией, отклоняется без сетевого
эффекта.

## Критерии приёмки

| Требование | Доказательство |
| ---------- | ------------- |
| `REQ-3801` | Unit/process test выпускает версию, сдвигает draft и проверяет, что план построен из записанной ревизии и exact artifact digest. |
| `REQ-3802` | Registry и transport tests фиксируют три отдельные команды и обязательное подтверждение точного hash. |
| `REQ-3803` | Mock transport теряет ответ, видит один ключ на повторах; ошибка предлагает status по известному plan id. |
| `REQ-3804` | Contract tests проверяют bearer header и отсутствие запрещённых полей в request/output/error. |
| `REQ-3805` | Fixture corpus покрывает happy path, отказ полномочий, replay и восстановление для grants и reports. |
| `REQ-3806` | Registry и transport tests покрывают все grant routes, повтор с одним ключом, обязательный confirm и отсутствие raw token в публичной поверхности команды. |
| `REQ-3807` | Process/unit corpus доказывает preview без HTTP, exact-digest confirm, сохранение после потерянного ответа, replay без второго эффекта и fail-closed diagnostics. |
| `REQ-3808` | Transport/registry tests фиксируют три read-only маршрута, bearer boundary, точные path/query и отдельные CLI views без утечки в OpenAPI. |
| `REQ-3809` | Unit/registry/schema tests фиксируют owner-only запись без перезаписи, полный signed payload, порчу подписи, несовпадение exact coordinates, дубли и закрытую CLI-only схему. |
| `REQ-3810` | Unit tests планируют сетап с публичным и непубличным пином и проверяют, что план создан только для непубличного, а публичный перечислен как `already_published`; локальная `visibility` при этом противоречит ответу платформы. |
| `REQ-3811` | Digest считается над упорядоченным списком; смена порядка, добавление участника и другой `plan_hash` дают другой digest, а смена состояния плана — тот же. Повторный plan заменяет открытый набор той же версии. |
| `REQ-3812` | Confirm без флага отклоняется типизированной ошибкой; отказ второго из трёх участников оставляет первого опубликованным, набор `partial` и третьего неподтверждённым; чужой аккаунт или устройство отклоняются. |
