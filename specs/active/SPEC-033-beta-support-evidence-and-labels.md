# SPEC-033: Публичные метки beta-поддержки, доказательства и их свежесть

## Цель

Issue #193 должна сделать наблюдаемым фактический уровень поддержки харнесса в
API и web после выполнения связанных задач P11-01, P11-02 и P11-03 для Pi,
OpenCode и Grok Build. Пользователь должен видеть не только имя харнесса, но и
основание метки `beta`, состояние доказательств и их свежесть.

Эта спецификация дополняет `SPEC-001`, `SPEC-008`, `SPEC-021` и `SPEC-022`.
Доменная и wire-модель публичного read-model принадлежит
`ADR-0072-public-beta-support-evidence-read-model.md` и контрактам в
`docs/contracts/`.

## Границы

Входят:

- публичная модель уровня поддержки `primary` или `beta`;
- безопасная публичная проекция evidence для поддержки харнесса;
- состояния свежести и пригодности evidence;
- фильтры API и web по уровню и состоянию поддержки;
- beta-метки, evidence и freshness на карточках и страницах каталога;
- двуязычные сообщения и одинаковая семантика API и web;
- фикстуры и отрицательные проверки для `stale`, `missing` и `not_verified`
  evidence.

Не входят:

- реализация Pi, OpenCode или Grok Build provider;
- изменение CLI, локального реестра или канонического Agent Skill;
- изменение `trust_lane`, `author_verified` или `component_verified`;
- автоматическое повышение beta до primary;
- блокировка первого MVP-релиза из-за неполноты beta evidence;
- публикация секретов, внутренних логов, credentials или приватных артефактов.

## Термины

- **Support tier** — заявленный продуктовый уровень поддержки харнесса: `primary`
  или `beta`.
- **Support evidence** — проверяемая запись о точном provider release и
  результате его сквозной проверки для конкретной матрицы среды.
- **Freshness** — результат сравнения текущего времени с допустимым сроком
  evidence.
- **Support state** — публичное состояние линии поддержки: `verified`,
  `stale`, `missing` или `not_verified`.

Support tier и support state — независимые поля. `beta` не означает
`experimental`, а `experimental` не означает beta provider.

## Требования

- `REQ-3301`: API и web представляют support tier только значением `primary` или
  `beta`, причём значение соответствует каноническому набору харнессов из
  `SPEC-001` и не выводится из `trust_lane`.
- `REQ-3315`: Состав уровней задан ровно так: `claude-code`, `codex` и
  `grok-build` — `primary`; `pi`, `opencode`, `cursor` и `antigravity` — `beta`.
  Значение имеет одного владельца и не повторяется второй таблицей. Уровень является продуктовым
  решением: по `REQ-3306` evidence его не повышает, а по `REQ-3307` отсутствие
  записанного прогона отражается в support state и не понижает уровень.
- `REQ-3302`: Публичная карточка и точная версия объекта показывают support tier,
  support state и безопасную сводку evidence для `latest_harness_id`.
- `REQ-3303`: `support evidence` привязано к точному `provider release`, `exact
  commit` или `digest`, `harness`, `operating system` и `architecture`;
  доказательство без
  точного происхождения не может дать состояние `verified`.
- `REQ-3304`: `verified` выдаётся только при наличии всех обязательных evidence
  текущей support policy с результатом `passed` и неистёкшим сроком действия.
- `REQ-3305`: Истёкшее обязательное evidence получает состояние `stale`, а
  отсутствующее обязательное evidence — `missing`; ни одно из этих состояний не
  отображается как подтверждённая поддержка.
- `REQ-3306`: Evidence с результатом `failed`, `degraded`, `not_run` или иным
  результатом, не принятым политикой, получает `not_verified` и не повышает
  support tier.
- `REQ-3307`: Отсутствие или устаревание beta evidence отображается честно и не
  блокирует первый MVP-релиз; линия без записанного запуска не называется
  поддержанной и получает `not_verified`.
- `REQ-3308`: Support evidence не изменяет `author_verified`,
  `component_verified` или `trust_lane`; эти оси продолжают вычисляться по
  `ADR-0016`, `ADR-0026` и `ADR-0032`.
- `REQ-3309`: Фильтры API принимают только объявленные значения support tier и
  support state, сохраняют остальные фильтры и не меняют request-scoped consent
  для линии `experimental`.
- `REQ-3310`: Web не вычисляет support state, freshness или пригодность evidence
  самостоятельно; он показывает значения канонического API read-model.
- `REQ-3311`: Русская и английская локали показывают одинаковые поля, состояния,
  причины и последствия; пользовательские строки не захардкожены в компонентах.
- `REQ-3312`: Публичная проекция не содержит credentials, секретов, внутренних
  логов, приватных object keys, непубличных URLs или данных, позволяющих получить
  доступ к evidence artifact.
- `REQ-3313`: Каждая публичная запись evidence содержит безопасные идентификаторы
  проверки, источник, exact release reference, `observed_at` и, если применимо,
  `expires_at`; timestamp не подменяется временем рендера web.
- `REQ-3314`: Существующие клиенты, не знающие аддитивные поля, продолжают
  декодировать поддерживаемую major-версию API; новые клиенты отвергают
  неизвестные значения enum и безопасно показывают `not_verified` только по
  правилам контракта, а не по отсутствию поля.

## Состояния и ошибки

Канонические состояния support evidence:

```text
verified      обязательные evidence есть, passed и ещё действуют
stale         обязательное evidence было, но его срок истёк
missing       обязательное evidence не было опубликовано
not_verified  evidence есть, но не проходит текущую policy
```

Невалидный или несовместимый фильтр возвращает типизированную ошибку API.
Повреждённая или противоречивая серверная запись не превращается в `verified`:
сервер отвечает безопасной ошибкой или проектирует `not_verified` по правилам
`ADR-0072`. Web показывает состояние зависимости и `X-Request-Id`, не раскрывая
внутреннюю причину.

## Безопасность и приватность

Support evidence является публичной метаинформацией, а не публичным доступом к
артефакту. Публичный клиент не получает storage key, подпись, токен, приватную
ссылку или содержимое отчёта. Provider release проверяется по существующей
политике доверия, а подтверждение происхождения не означает, что платформа
безопасна во всех сценариях.

Статус `verified` не даёт права на установку и не переводит объект в
`authoritative`. Установочная пригодность и trust lane остаются отдельными
решениями.

## Совместимость и миграция

Изменение wire-полей выполняется аддитивно через канонические модели
`packages/contracts`, generated schemas и OpenAPI. Web-клиент пересоздаётся из
обновлённого контракта. Existing catalog rows получают безопасное состояние
`missing` до импорта соответствующего evidence; исторические публикации и их
паспорта не переписываются.

Rollback отключает новые фильтры и проекцию support evidence, сохраняя старые
поля каталога и исторические evidence. Удаление evidence или пересчёт статуса
не удаляет опубликованные версии и не изменяет уже установленные targets.

## Критерии приёмки

| Требование | Исполнимый oracle |
|---|---|
| `REQ-3301` | Contract test принимает только `primary`/`beta` и доказывает независимость от `trust_lane`. |
| `REQ-3315` | Тест доказывает точный состав уровней и то, что вторая таблица уровней в дереве отсутствует. |
| `REQ-3302` | API и web golden tests находят tier, state и evidence summary на card и exact-version routes. |
| `REQ-3303` | Negative test отклоняет evidence без exact release, digest или matrix context. |
| `REQ-3304` | Fixture с полным свежим набором passed evidence получает `verified`. |
| `REQ-3305` | Fixtures с истёкшим и отсутствующим обязательным evidence получают `stale` и `missing`. |
| `REQ-3306` | Fixture с failed/degraded/not_run evidence получает `not_verified`. |
| `REQ-3307` | Release gate проверяет, что неполная beta-линия не блокирует MVP и не называется supported. |
| `REQ-3308` | Contract test изменяет support evidence и подтверждает неизменность trust axes. |
| `REQ-3309` | API tests проверяют enum validation и независимость от experimental consent. |
| `REQ-3310` | Static/component test запрещает web-side status computation. |
| `REQ-3311` | Locale parity test сравнивает ru/en поля, состояния и действия. |
| `REQ-3312` | Secret/privacy scan и response inspection не находят запрещенных значений в публичной проекции. |
| `REQ-3313` | Schema test требует provenance и timestamps и запрещает render-time freshness. |
| `REQ-3314` | Compatibility test принимает старый additive response и проверяет безопасную обработку новых enum. |
